**1a. Re-ejecutar los queries del Plan 01, identicos.** Volcar a `baseline/fichaje-despues.txt`
con el mismo formato que `fichaje-antes.txt` — si el formato difiere, el diff da ruido y la
verificacion pierde valor.

```sql
SELECT p.oid::regprocedure AS firma,
       p.prosecdef AS secdef,
       md5(pg_get_functiondef(p.oid)) AS huella
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public' AND p.proname LIKE 'fichaje%'
ORDER BY 1;
```
Mas la seccion `-- TABLAS` (columnas, RLS, policies) y los rowcounts de las 6 tablas.

**1b. Diff explicito, fila por fila.** No basta con que ambos archivos "se vean parecidos".
Comparar programaticamente:
```powershell
$antes  = Get-Content .planning/phases/03-.../baseline/fichaje-antes.txt
$despues= Get-Content .planning/phases/03-.../baseline/fichaje-despues.txt
Compare-Object $antes $despues
```

Requerido: **salida vacia** en la seccion de firmas y huellas.

Que significa cada divergencia:
- **Cambia una `huella` md5** → alguna funcion `fichaje_*` fue redefinida. Grave: el DDL de la
  fase toco algo que no debia. Investigar cual y restaurarla desde el historial de migraciones.
- **Falta una firma** → una funcion desaparecio. Muy grave: rollback inmediato.
- **Aparece una firma nueva** → alguien mas escribio en la base durante la fase. Registrarlo; no
  es culpa de esta fase pero invalida la comparacion.
- **Cambia un rowcount** → uso normal del modulo (alguien ficho mientras corria la fase). **No es
  falla.** `fichaje_fichadas` es una tabla transaccional. Distinguirlo con claridad de un cambio
  estructural: lo que no puede cambiar son columnas, RLS y policies.

**1c. Registrar el veredicto sin ambiguedad** en `fichaje-despues.txt`, con una de estas frases:
- `VEREDICTO: fichaje_* INTACTO — N firmas, N huellas identicas, estructura de tablas sin cambios`
- `VEREDICTO: fichaje_* ALTERADO — <detalle exacto de la divergencia>`
