## Hallazgo 1 — DATA-01: cual overload sobrevive NO es el mismo criterio en los dos pares

El briefing de la fase decia "la version sin argumentos es la corregida, quedarse con la segura".
Eso es cierto para un par y **falso para el otro**. Verificado por grep sobre ambos codebases:

### `get_my_linked_customers` → conservar `()`, dropear `(p_auth_user_id uuid)`

| | |
|---|---|
| Callers en Elias | ninguno (frontend sin portar) |
| Callers en PaginaLK | `historial.js:354`, `script.js:8183`, `sugerencias.js:237` — los 3 **sin argumentos** |
| Seguridad | `()` usa `auth.uid()`. `(p_auth_user_id uuid)` recibe el uuid como parametro: pasar otro uuid devuelve la cartera ajena |

Aca seguro y consumido coinciden. Dropear `(p_auth_user_id uuid)` sin dudar.

### `get_products_public_sorted` → conservar `(sort_mode text)`, dropear `()`

**Esto invierte el criterio del briefing.** El overload sin argumentos es el muerto:

| | |
|---|---|
| Caller en Elias | `script.js:772` → `rpc("get_products_public_sorted", { sort_mode: sortMode })` |
| Caller en PaginaLK | `script.js:1023` → identico, **con** `sort_mode` |
| Origen | `()` viene de `migration_tn.sql:337` (viejo); `(text)` de `migration_tn_fix3.sql:202` (nuevo) |

Los dos frontends —el actual y el que se porta en la Phase 4— pasan `sort_mode`. Dropear el
`(text)` romperia el catalogo en ambos. La seguridad no es el eje: es catalogo publico, granteado
a `anon` por diseño.

**Trampa del GRANT.** `script.js:772` cae en la rama `if (!logged)`, o sea contexto `anon`. Los
archivos muertos sugieren que `()` estaba granteado a `anon` pero `(text)` solo a `authenticated`.
Si el Plan 01 confirmo eso, dropear `()` sin grantear `(text)` a `anon` **deja el catalogo vacio
para todo visitante no logueado**. Leer la frase exacta del `03-01-SUMMARY.md`.

**Efecto lateral util:** con `(sort_mode text DEFAULT 'ranking')` ya presente, dropear `()`
tambien arregla las llamadas sin argumentos — el default cubre ese caso. La ambiguedad desaparece
por completo.

criterio de la fase: un no-admin pidiendo un `cod_cliente` ajeno recibe rechazo (el codigo es

**2b. `language sql` → `plpgsql` donde haga falta.** Una funcion `language sql` no puede hacer
`RAISE EXCEPTION`. El `03-01-SUMMARY.md` dice cual es cual. Para las `sql`, envolver:
```sql
LANGUAGE plpgsql SECURITY DEFINER SET search_path = 'public' STABLE
AS $$

  RETURN QUERY <la consulta original, sin cambios>;
END;
$$;
```
Preservar exactamente: `SECURITY DEFINER`, `SET search_path = 'public'`, `STABLE`, y **la firma y
el tipo de retorno**. Si el `RETURNS TABLE(...)` cambia aunque sea en un tipo, PostgREST empieza a
devolver otra forma y `admin.js` deja de parsear.

**2c. `CREATE OR REPLACE` siempre que la firma no cambie.** Preserva el ACL. Si alguna exige
`DROP` + `CREATE` (Postgres no permite cambiar el tipo de retorno con REPLACE), hay que
**re-emitir los GRANT** desde `baseline/grants-antes.txt` en la misma transaccion — un DROP borra
el ACL y la funcion queda inejecutable para `authenticated`. Marcar esos casos con
`-- ATENCION: drop+create, requiere re-GRANT`.

**2d. `SET search_path = 'public'` no es decorativo.** Estas son `SECURITY DEFINER` y consultan
`public.admins`. Sin search_path fijo, un caller puede anteponer un esquema con su propia tabla
`admins` y auto-otorgarse permiso. Ademas schema-calificar `public.admins`, `public.customers`,
`public.user_customer_links` dentro de los guards.
